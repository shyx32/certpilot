# 架构设计

这份文档记录**为什么这样设计**。做了什么看代码就够了，为什么这么做才是容易丢失的部分。

## 五条原则

**一次配置，长期免维护。** 证书系统最大的失败模式不是签不出来，而是三个月后没人记得它怎么工作。
所有需要人工介入的动作都设计成「首次接入时做一次」，续期路径上不允许出现任何需要人操作的环节。

**验证与部署彻底解耦。** 「怎么证明域名是我的」和「证书发到哪里去」是两件独立的事。
一张 `*.example.com` 证书可以用 DNS-01 签出来，同时推给多个 CDN 域名和多台 Nginx。两侧都是插件。

**签发成功 ≠ 上线成功。** 流水线的终态是 `verified`（外部拨测确认线上指纹已更新），不是 `issued`。
没有这一步，整套系统只是个「看起来在工作」的定时任务。

**一切幂等，随时可重放。** 进程可以在任意一步被杀掉。ACME Order URL、证书指纹、任务阶段全部落库，
重启后从上次状态继续，而不是重新申请一张——CA 的速率限制不允许反复试错。

**私钥是最高密级。** 数据库拿到手也解不开：信封加密，主密钥不在库里。

## 为什么是三个容器

按 1000 个域名的上限测算：

| 维度 | 量级 | 结论 |
| --- | --- | --- |
| 签发任务 | 1000 ÷ 60 天 ≈ 17 次/天 | 日均忙碌 < 1.5 小时 |
| 巡检拨测 | 1000 次/天，单次 ~200ms | 10 并发约 20 秒跑完 |
| 数据总量 | 加上保留策略约 10 万行 | 永远不需要考虑分库分表 |

这是一个几乎全天空闲的系统。Redis 队列、独立 worker 进程、多实例部署都是为不存在的负载支付复杂度。
队列用 PostgreSQL 的 `SELECT … FOR UPDATE SKIP LOCKED`，单飞用 `pg_advisory_lock`。

`api` 镜像同时提供 `serve` 与 `worker` 子命令。真要拆时改的是编排文件，不是代码——这是留白，不是现在要用的功能。

## 参考了 Uptime Kuma，但有一处不能照搬

值得借鉴的：一条命令装完、WebSocket 实时推送、provider 目录模式、数据保留策略、可分享的只读看板。

**不能照搬的是它的无状态探测模型。** Kuma 的探测丢一次无所谓，进程重启重新探一遍就行。
而 ACME 签发是有状态的多步事务（创建 Order → 投放 challenge → 等 CA 校验 → finalize），
中途重启若把状态丢在内存里，重来一遍就等于向 CA 重新申请一张。

轻量化可以砍容器、砍中间件，但不能砍持久化状态机。

## 域名到 DNS 账号的自动识别

录入凭据时立刻拉取该账号下全部 zone 并落库。之后用户只输域名，系统做**最长后缀匹配**：

```
输入 a.b.example.com
  已托管 zone: example.com(凭据#1)、b.example.com(凭据#2)
  取最长匹配 → 凭据#2
  TXT 写在 zone b.example.com 上，主机记录 _acme-challenge.a
```

**同一个域名在不同 zone 划分下主机记录并不相同**，这一步不能想当然：

| 域名 | zone | 主机记录 |
| --- | --- | --- |
| `a.b.example.com` | `example.com` | `_acme-challenge.a.b` |
| `a.b.example.com` | `b.example.com` | `_acme-challenge.a` |
| `*.example.com` | `example.com` | `_acme-challenge` |

用 provider 返回的真实 zone 列表来算是唯一可靠的办法。

这一步顺带解决了凭据健康检查：每天刷新一次，AK 失效当天就暴露，而不是等到六十天后续期时才发现。

## 错误信息是产品的一部分

云 SDK 与 ACME 库的原始错误带着 RequestId、响应头乃至整个 header map，
直接抛给用户既看不懂也无从下手。所以有两个翻译层：

- `internal/aliyun/errors.go` — 阿里云错误码 → 可行动的中文
- `internal/acme/errors.go` — ACME problem type → 可行动的中文

它们还承担一个功能职责：**判断该不该重试**。

`IsPermanent` 基于 problem type 判断永久性失败（域名被 CA 拒绝、CAA 不允许、邮箱不合法）。
这类错误必须一次就停——CA 对失败验证有独立配额，拿着注定被拒的域名反复重试会耗光配额并可能触发风控。
而 `rateLimited` 与 `serverInternal` 相反，必须继续退避重试，放弃会让证书静静过期。

> 实现上有个坑：lego 把多域名失败聚合成不支持 `Unwrap` 的错误，而我们自己的 `Error()` 又已经清洗掉了 URN。
> 所以 `IsPermanent` 要沿 Unwrap 链把每一层的**原始文本**都翻一遍。仓库里有对应的回归测试。

## RAM 子账号自动创建

「请去控制台创建 RAM 子账号，粘贴这段 JSON」——这段说明写在文档里，实际结果是大部分人嫌麻烦直接填了主账号 AK。
**最小权限如果需要额外操作才能获得，它就不会发生。**

四步 API：`CreateUser` → `CreatePolicy` → `AttachPolicyToUser` → `CreateAccessKey`。

三条硬规则：

1. **管理凭据不入库、不落盘、不记日志**，只存在于本次请求的内存中
2. **`AccessKeySecret` 只返回一次**——入库失败必须立刻 `DeleteAccessKey` 撤销，
   否则会在用户账号里留下一把谁也不知道密码的僵尸 AK
3. **任一步失败反向回滚**已创建的资源，让账号回到干净状态

创建前把完整策略 JSON 展示给用户。一个索要管理凭据的功能，透明度就是它的信任基础。

## 部署与生效校验

阿里云 CDN 走两段式：先上传到 CAS 拿 `CertId`，再绑定到各域名。
一张证书传一次绑 N 个域名，出问题能直接切回上一个 `CertId` 回滚。

单个域名绑定失败不中断其余域名——10 个里 1 个出错，其余 9 个照常完成。

`Deploy` 返回成功只说明请求被接受。`Verify` 直接与每个域名握手比对指纹，
在目标的生效窗口内带退避重试（CDN 用 30 秒起、最长 10 分钟的窗口）。
超时未匹配标记为「已下发但未确认生效」——这个状态比单纯的失败更需要人看一眼。

## 部署到 Nginx：三个反直觉的地方

**一、写入权限与重载权限是两件事。**
证书目录常常属于运维用户，而 nginx master 由 root 启动。
能写文件不代表能向它发 HUP 信号，`nginx -T` 同样需要提权才能读到完整配置。
这两类权限必须分开探测——合成一个判断会在部署的最后一步才失败，
而那时证书已经替换了一半。

**二、named volume 不能直写。**
`docker inspect` 确实会给出 `Source`（`/var/lib/docker/volumes/<name>/_data`），
但那是个属主 root、权限 700 的目录。在 `docker` 组里意味着能**指挥 daemon**，
不意味着能用自己的身份读写它。所以 named volume 的默认策略是辅助容器：

```
docker run --rm -i --volumes-from <nginx> <同一个镜像> sh -s -- <参数>
```

`--volumes-from` 继承全部挂载，镜像复用 nginx 自己的（本来就在本地，零额外拉取）。
这条路径对 bind mount 与 named volume 一视同仁，也不必知道宿主机路径。

**三、先替换，再预检。**
直觉上该先验证再替换，但 `nginx -t` 读的是配置里写死的那个路径——
新证书还躺在 `.new` 里时，预检验的仍是旧文件，等于没验。

而替换磁盘文件对正在运行的 nginx 是安全的：它用的是内存里已加载的证书，
只有 reload 才会重新读盘。所以顺序是 **写 .new → 原子替换 → 预检 → 重载**，
任何一步失败都回滚。这样预检才真正验到新证书，而线上服务全程不受影响。

> 这三条都是集成测试打出来的。前两条来自「跑不通」，第三条来自一个
> **测试通过但行为错误**的场景：下发一份非法证书，预检居然通过了，
> 直到 reload 才失败——因为预检根本没看新文件。

## SSH 命令的安全边界

SSH 的 exec 请求本质上是把一整个字符串交给远端登录 shell，
没有 `execve` 那样「参数即数据」的保证。所以转义必须在这一层做实：

- 调用方永远传 `argv` 数组，由 `sshx.BuildCommand` 逐个转义后拼接
- 单引号包裹，内容里的单引号用 `'\''` 闭合再拼接
- 占位符（`{container}` 等）展开后仍然只是某个 argv 元素，不会成为代码

原子替换要做备份、改名、改权限，绕不开 shell。边界在于：
**脚本文本是代码里的常量，变量只通过 `$1 $2` 进入**，全程不做字符串拼接。
证书内容用 base64 作为参数传入——脚本本身已占用 stdin，两者不能共用，
而 base64 顺带免去了对 PEM 里换行与引号的担心。

集成测试里有一条专门验证这件事：把 `; rm`、`$(...)`、反引号等作为参数发过去，
断言回显与输入完全一致、且没有产生任何副作用文件。单元测试只能证明
转义函数的输出形状，这条才证明它在对端真的成立。

## 安全

- 接口默认全部需要登录，没有「内网所以不设防」的例外
- 信封加密：每条记录独立数据密钥（DEK），DEK 由主密钥（KEK）加密。
  加密时绑定记录标识作为 AAD，防止密文被搬到另一条记录上复用
- 初始密码随机生成并只打印一次，不存在 `admin/admin` 这样的默认口令
- 凭据写操作与 RAM 子账号创建限管理员角色
- 审计日志记录谁在什么时候做了什么，但绝不记录凭据本身

## 巡检是整套系统的验收机制

签发系统能告诉你「我签成功了」，但回答不了「线上现在跑的是哪一张」。
巡检就是为这个问题存在的，其中**指纹比对**是最核心的一项：
把线上握手拿到的证书指纹和本地最新一版比对，不一致就意味着
续期完成了但没有生效——这种故障不会有任何报错，只会在几个月后突然过期。

判读时刻意不做信任校验（`InsecureSkipVerify`）。原因是我们要看的是
「服务端实际发了什么」，而不是「Go 的根证书库认不认」。
链是否完整、是否自签，都由判读逻辑单独给出结论——
这样自签或链不全的情况才能被观测到，而不是直接连不上。

缺中间证书是单独一条检查：浏览器会自己补全，部分 App 与 Java 客户端却会失败。
这类故障最容易漏，因为「我这儿打得开」。

## 告警的设计目标是让人愿意看

20 个域名同时到期应该是一条消息，而不是 20 条。刷屏的告警等于没有告警。
因此巡检把一轮发现汇总成单条通知，严重的排前面，超过 15 行折叠成一句
「还有 N 项，详见看板」。

另一个容易踩的坑：钉钉、企业微信、飞书这些平台**业务失败时也返回 HTTP 200**，
只在响应正文里给 errcode。不解析它就会出现「界面显示发送成功、群里什么都没有」。
所以每个渠道都要检查平台自己的错误码，并把原因带回给用户。

## CA 配额是最稀缺的资源

Let's Encrypt 对每个注册域每周的签发量有硬限制，一旦撞上，
**整个注册域会被锁一整周**——那时想签任何一张新证书都不行。

所以本地保留了一份计数，默认阈值比官方配额低 20%：接近时主动停下并告警。
主动停下的代价（人来看一眼）远小于撞墙的代价（一周内无法签发）。

同一逻辑体现在错误分类上：`rejectedIdentifier`、`caa` 这类
CA 明确拒绝的错误一次就停，而 `rateLimited`、网络抖动必须继续退避重试——
误判前者会浪费配额，误判后者会让证书静静过期。

## 已知取舍

| 不做 | 原因 | 什么情况下再捡起来 |
| --- | --- | --- |
| Agent 模式 | 假定目标服务器可直连，必要时经跳板机 | 出现大量无法直连的内网服务器 |
| 高可用多副本 | 停机数小时不影响线上业务，续期有 30 天余量 | 基本不会——精力该投在备份验证上 |
| 多租户隔离 | 单团队自用，RBAC 足够 | 要作为平台开放给多个业务方 |
| Redis / 独立 worker | 日均十几个任务，PostgreSQL 完全够用 | 域名规模超过一万时重新测算 |
